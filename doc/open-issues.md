## 2. 会话与连接（P1）

### #2 240 帧断连挪不到安全点 —— **已修（`91b0160`），待部署**
- **现象**：F0 推送序号 SDK 只接受 1~251，前置攒满 240 条就 `Close`，活跃行情下几秒一次，与报单突发正面撞车。
- **旧实现在哪错**：`_rtnRecycleDue` 一置位就 `Close()`——不管出站队列里还压着几帧，那些帧连同序号一起丢，
  客户端重连后也补不回来；而且没有 251 那道硬闸，越过可接受域之后客户端是**静默卡死**（不报错、不重连）。
- **现在怎么做**：软点 240 只打标；**安全点 = 出站排空 + 不在派发 + 捕获集为空**，此时才 `Close`；硬顶 251 兜底立即断并丢该帧。
  写循环尾和 `RoutePush` 各查一次。
- **实现坑（已记进 `DESIGN.md` §3.11）**：`ChannelReader<T>.Count` 在本运行时对无界 channel 抛
  `NotSupportedException`，第一版直接读它，写循环在手握响应之后立刻死了（E2E 表现「连上了不回包」29s 超时）。
  改成自记账 `_outPending` 后 12s 通过。
- **还剩什么**：① 部署（§1.1 第 1 步）；② 部署后在真实负载下确认「240 后 1~2s 内出现认证/登录行」。
- **落点**：`src/Ctp.Net.Front/CtpFrontSession.cs`（`TryRecycleAtSafePoint` / `TryBeginRecycle` / `EnqueueOutbound`）。
- **细节**：`../../ctp-net-client/doc/session-reauth-after-reconnect.md` §3.1、`../../ctp-net-client/doc/session-lifecycle.md` §5A。

### #3 `FrontConnected` 的闸门仍然依赖回调顺序

- **下一步**：**必须先做 #4**（会话日志），拿到一次真实断连的回调序列，再决定闸门怎么写。
- **落点**：`ctp-net-client/src/Ctp.Net.Client/CtpSessionService.cs`（`OnTraderFrontConnected` / `OnSafetyTimer`）。
- **细节**：`../../ctp-net-client/doc/session-reauth-after-reconnect.md` §3.4、§7「仍缺」第 1 条。

### #4 bot 会话日志 —— **已部署（2026-10-30 11:30）**
- **现象（历史）**：为治「日志撑爆磁盘」（单 bot 8.6 GB/天）把 bot stdout 改成了 `>NUL`，于是客户端侧零证据。

- **现象**：客户端发 `ReqQryOrder`，前置回「账本 6308 条，回 200 行」，连接被对方 RST：
  前置侧 `会话异常: …远程主机强迫关闭了一个现有的连接`，客户端侧 `[ctp-trader] 前置断开 reason=4097`
  → 自动重连 → 重新登录。后果：查报单拿不到结果，还白搭一次重连（把在途动作搅进对账）。
- **根因（实测定案）**：**响应流水号重复**。旧实现把每行记录帧的 80 族流水写成「首行回显请求计数器、其后 +1」，
  于是同一连接里前一个查询（持仓）刚用过的流水号又被报单行重复使用；官方 `thosttraderapi_se` 见到重复的流水
  就停止派发并 RST。
- **推理过程中被推翻的两个错误假设**（记下来，免得后人再走一遍）：
  1. ~~「单帧 89200B 溢出 2 字节长度域」~~ —— 按字节封顶到 60000（实测帧 59764B）**仍然断**；
  2. ~~「单次写的字节量超过 SDK 约 4KB 的收包缓冲」~~ —— 改成逐帧写（每帧 446B）**仍然断**，
     客户端照样只收下 11 帧就 RST。
  真正把两个错误假设排除的是这组对照：
  | 实验 | 结果 |
  |---|---|
  | 每行回显请求计数器、+1（旧） | 1 行 ✅ `报单查询响应 ErrorID=0 isLast=True`；≥2 行 ❌ 必断 |
  | 每行取新的 `NextQrySeq()`（与持仓/资金同款，**现版本**） | **200 行 / 89KB 一次查询，0 断连** |
  关键判据是「1 行通、2 行断」——大小假设解释不了，序号重复解释得通（单行时没有第二次用到同一个号）。
- **改法**：`src/Ctp.Net.Front/CtpFrontSession.cs` 查报单分支改为 `BuildQryOrderRsp(NextQrySeq(), …)` 逐行取新流水；
  同时把四处多行应答（持仓/成交/报单/合约）统一收进 `EnqueueRecords`——一行一帧、一帧一次 TCP 写
  （真前置同款；客户端 wrapper 本来就靠静默期收尾收集多行）。**没有**保留字节封顶：它会静默丢行，
  而丢行的理由已被证伪。
- **验证（2026-10-30 12:41 部署，无任何环境变量）**：`build-tools/probe-diag.ps1 -User botmm`
  → `前置断开` **0 次**、`报单查询响应` **200 行**、资金/持仓正常、客户端 stderr 空。
- **顺带修正的旧结论**：10-24 记的「记录帧该槽必须等于请求值，写自己的序列号会被 SDK 丢弃」**已被推翻**，
  代码注释已同步改写。
- **仍未覆盖**：本轮只在 botmm 账户（账本 7000+ 条、200 行封顶）验过；行数封顶 200 仍是「真前置只回当日委托」
  的近似，账本超 200 条的账户仍只回 200 行（活单优先）。`CtpTrader` 侧多行收集靠静默期收尾，
  若将来行数放宽到几千行，要重新确认静默期是否够。
- **细节**：`FEATURE_MATRIX.md` §2 `ReqQryOrder` 非空行。

## 7. 不要做的事（避免重复踩坑）

1. **不要给记录帧「加宽」量槽/状态槽**——定宽遍历，多一字节就整体失步（2026-10-13 断连风暴）。
2. **不要在没有阳性对照的情况下做槽位探针**——「改了没反应」既可能是槽不对，也可能是探针没生效；
   2026-10-29 的假阳性（1 手样本 vs 捕获常量同值）就是这么来的。
3. **不要把「去重跳过 N」当行情健康指标**——它衡量的是簿变更 vs 上报字段变化，见 `doc/md-tick-delivery.md` §6。
4. **不要在断连窗口里「重发」报单**——先查后补（对账），报单不幂等。
