## 2. 会话与连接（P1）

### #2 240 帧断连挪不到安全点
- **现象**：F0 推送序号 SDK 只接受 1~251，前置攒满 240 条就 `Close`，活跃行情下几秒一次，与报单突发正面撞车。
- **现在兜到哪**：客户端 Ready 门禁（不在断线窗口发帧）+ 登录对账（丢了能补）——**后果被兜住，触发源没动**。
- **为什么不直接改**：需要一个「安全点」判据（无在途报单回报 + 出站队列空 + 距上次业务帧短静默），
  而这些状态目前在会话里是分散的；随手加个延时只会把断连挪到更随机的位置。
- **下一步**：在 `CtpFrontSession` 里显式维护 `_inFlightRsp` 与出站队列深度，写成一个 `SafeToClose()`，
  再拿 `CtpFrontE2eTests` 的 240 用例扩一条「断连时无在途」断言。
- **落点**：`src/Ctp.Net.Front/CtpFrontSession.cs`（`_rtnRecycleDue` 分支）。
- **细节**：`../../ctp-net-client/doc/session-reauth-after-reconnect.md` §3.1、`../../ctp-net-client/doc/session-lifecycle.md` §5A。

### #3 `FrontConnected` 的闸门仍然依赖回调顺序
- **现象**：`OnTraderFrontConnected` 里还是 `if (_hadLoggedIn && !_socketAlive)`。服务端主动 `Close` 时，
  如果 SDK 只回调 `FrontConnected` 不回调 `FrontDisconnected`，重连就不会触发。
- **为什么不直接改**：2026-10-29 事故后仍然**没有客户端侧证据**能区分「SDK 不回调」还是「被别处重置」。
  在没日志的情况下改成无条件重建，可能引入重连风暴（比现在更糟）。
- **下一步**：**必须先做 #4**（会话日志），拿到一次真实断连的回调序列，再决定闸门怎么写。
- **落点**：`ctp-net-client/src/Ctp.Net.Client/CtpSessionService.cs`（`OnTraderFrontConnected` / `OnSafetyTimer`）。
- **细节**：`../../ctp-net-client/doc/session-reauth-after-reconnect.md` §3.4、§7「仍缺」第 1 条。

### #4 bot 会话日志未恢复
- **现象**：为治「日志撑爆磁盘」（单 bot 8.6 GB/天）把 bot stdout 改成了 `>NUL`，于是客户端侧零证据。
- **下一步**：只记 `连接 / 认证 / 登录 / 断开(reason) / 重连 / 会话重建`，按天轮转 + 单文件上限（如 8 MB × 7），
  不记逐笔、不记查询。成本约几十 KB/天。
- **落点**：`aether-ctp-hosts/scripts`（启动脚本与计划任务）。
- **细节**：`session-reauth-after-reconnect.md` §5 P2。

## 3. 持仓与查询记录（P1/P2）

### #5 持仓其余字段仍是抓包常量

  `UseMargin` / `PositionProfit` / `CloseProfit` 仍是 2026-10-03 抓包里的值。
- **证据**：0..260 **全量单字节扫描**没有任何一个字节能影响这五个字段（捕获值 33790.00 / 4730.60 / -20.00 恒不变）
  ⇒ 要么是多字节定点/浮点编码，要么本帧压根没有这些槽。
- **下一步**（按顺序，别跳）：
  1. 拿一条**真前置**的持仓样本：昨仓非 0、成本/保证金非默认（SimNow 隔夜仓最容易造）；
  2. 用 `CtpFrontTemplates.QryPositionRecordHook`（`internal`，生产恒 null）做逐字节 patch-scan，
     **必须带阳性对照**（先改已知正确的 @54，确认补丁可见）；
  3. 定位后按 `Edit` 定宽写入；槽位定死前不要合并。
- **落点**：`src/Ctp.Net.Front/CtpFrontTemplates.cs`（`BuildQryPositionRsp`）。
- **细节**：`DESIGN.md` §3.10。

### #6 持仓量 >255 被截到 255
- **现状**：总仓/今仓都是 1 字节槽（0..255 实测逐值可用）。>255 时前置**截到 255 + 日志**。
- **为什么不直接加宽**：记录帧是定宽遍历的，多一个字节会让后续字段整体后移——那正是 2026-10-13 断连风暴的成因。
- **下一步**：要么从真前置抓一条 >255 的持仓样本、看它怎么编码（可能换成 `E7 <多字节>` 或走二进制族），
  要么接受截断并在桌面端做提示。**在有样本前，禁止「凭感觉撑宽」。**
- **落点**：同上；边界由 `FrontPositionFieldsTests.超过单字节槽的持仓_按255上报而不是写坏帧` 钉住。

### #7 查合约空结果不派发（客户端 30s 超时）
- **现状**：过滤到不存在的合约 ⇒ 前置直接不回帧；真前置会派发「空记录 + isLast」。
- **为什么不做**：op=01 转发空记录会让 SDK 交出无效指针 ⇒ C# `Marshal.PtrToStructure` 段错误（6.6GB core dump 那次）。
- **下一步**：需要一条 op=01 的**同会话请求 + 空应答配对帧**，把应答头做对再打开转发。
- **落点**：`CtpTrader.OnRspQryInstrument` 的空记录分支 + `CtpFrontSession` 查合约分支。
- **细节**：`DESIGN.md` §5「空记录回调不能盲转」、`FEATURE_MATRIX.md` §4。

### #8 查结算单非空正文未实现
- 只回 13B 空表（与真前置对「无结算单账户」的形状逐字节一致）。非空正文是分片大文本，槽位错即整帧被丢。
- **下一步**：找一个**真有结算单**的账户抓样本（SimNow 测试账户 4 个交易日全空）。
- **细节**：`DESIGN.md` §6 #6c。

### #9 查投资者（`ReqQryInvestor`）记录帧未逆向

## 5. 交易语义与编码（P2/P3）

- **#13 `OrderRef` 本地高水位**：现在仍取柜台 `MaxOrderRef` 初始化。跨进程重启/双会话下的回卷风险靠「同账户踢重」压住，
  但根上没解决。要做本地持久化高水位 + 与柜台值取 max。落点 `ctp-net-client`/`ctp-net-core`。
- **#14 撤单按 `(账户, OrderRef)` 定位**：交易所账本 `_byOrderRef` 是覆盖写。改用 `OrderSysID` 需要交易所侧支持，
  牵涉面大；现阶段靠踢重 + 账本对账规避。
- **#15 错误码 >255 降级 148**：`WireError` 把超 1 字节的核心码映射成 148，真码只进 GBK 前缀。
  要做映射表 + 结构化槽，得先抓包确认槽位。
- **#16 模板文件仍含历史会话字节**：头注写着含 token/密文/账号，原抓包已清空。重生成可能改帧宽，
  多行/tick 未逆向前不要盲重生成。
- **#17 分帧器/字段编解码器无独立单测**：`CtpFrameParser` / `CtpFieldCodec` 没有直接测试，心跳跨段未覆盖。
  成本很低（纯内存用例），只是一直没排期。

### #20 结算确认应答在官方 Windows 客户端下不被派发（2026-10-30 部署后实测新发现）

- **现象**：部署后的前置上，客户端 `LoginAsync` 里那句自动结算确认**每次都等 15s 超时**：
  `[ctp-trader] 结算确认失败（不影响登录）: The operation has timed out.`
  同一会话的认证/登录/成交回报/tick/资金/持仓**全部正常**，只是永远收不到结算确认回调。
- **前置侧证据**（`ctpsim-front.log`，09:53:08）：
  ```
  结算确认 #1 reqId=3
  → [69B] 020000410103344CE101E24014E301E102E19CE303E355E4D5FDC8B7EFEFEFEFEFE2
          040FE13F39393939E7626F746D6D20E73230323631303330E131313A31363A3536EFE7
  ```
  逐字段核对 = `SettleRspTemplate` 的 5 处 `Edit`（instance `01` / reqId `03` / broker `9999` /
  user `botmm ` / 交易日 `20261030`），**结构与 2026-09-29 抓的真前置帧完全同形**，没有可疑字节。
- **客户端侧证据**：`CtpTrader` 的结算确认回调（`CtpTrader.cs:691`）**一条日志都没有**——不是 ErrorID 非 0，
  是 SDK 根本没派发。
- **已排除**（别再重复）：①「客户端二进制旧」——console 二进制已用同一批构建更新后重跑，超时不变；
  ②「前置本地就先坏了」——本地 macOS 端到端 `官方SDK直连前置_登录结算资金持仓全链路` 358ms 跑完，
  两次结算确认都是 `ErrorID=0`。
- **已定性：平台差异**（2026-10-30 10:09 补上直接证据，不再是推测）。
  ① **跨公网实测**：从 macOS 客户端连**同一台远程前置**（`tcp://117.72.186.128:17801`，真实 TCP，
  不是 loopback），结算确认一次成功：`[ctp-trader] 结算确认响应 ErrorID=0 正确 reqId=3 isLast=True`。
  ⇒ 前置的 ⑫ 帧、字节、会话状态都没问题，**差别只在客户端**。
  ② **原生库证据**：服务器 `C:\Aether\ctp-console\publish` 里是官方 `thosttraderapi_se.dll`(3.4MB) /
  `thostmduserapi_se.dll`(3.0MB) + 22KB 胶水 `ctp_native.dll`；macOS 只有 `libctp_native.dylib`
  （**官方库没有 macOS 版**）⇒ 两平台跑的**根本不是同一套线协议解析实现**。
  ⇒ 自研实现解析宽松，官方 dll 严格：⑫ 模板只是**结构上**复刻了抓包，官方 dll 派发所需的某个附加条件没满足
  （额外 op/伴随帧/route 都可能）。这也是本仓最隐蔽的风险类别：**所有帧模板的验收基线一直是我们自己的客户端**。
- **注意一个没排掉的口子**：出站日志打在 `WriterLoopAsync` 的 `WriteAsync` **之前**，
  只能证明「准备写」，不能证明「写成功」。所以「帧没送到」这条还没被彻底排除。
- **下一步（按顺序做）**：
  1. ~~怀疑前置~~ → 已排除；改为在 **Windows 客户端侧**确认 69B 到底有没有到达（同机部署，直接在 `CtpTrader` 帧入口 dump，或 `netsh trace`）——
     这一步把「没送到」和「送到了没派发」彻底分开，是唯一的分叉点；
  2. 若到达：拿 2026-09-29 真前置抓包做**逐字节 diff**（不只字段值，含 ⑫ 前后相邻帧、route id、
     真前置是否在 ⑫ 之前发了伴随帧）；
  3. 若没到达：查写循环异常（`WriterLoopAsync` 的 `catch` 只记一行，会话仍活着）。
- **影响**：本交易所不强制「先确认结算再下单」，实测下单/撤单不受影响；但**客户端切回前置路径前必须弄清**，
  否则真实柜台语义下这是「第一天不能下单」。
- **落点**：`src/Ctp.Net.Front/CtpFrontTemplates.cs`（`SettleRspTemplate` / `BuildSettleRsp`）、

## 7. 不要做的事（避免重复踩坑）

1. **不要给记录帧「加宽」量槽/状态槽**——定宽遍历，多一字节就整体失步（2026-10-13 断连风暴）。
2. **不要在没有阳性对照的情况下做槽位探针**——「改了没反应」既可能是槽不对，也可能是探针没生效；
   2026-10-29 的假阳性（1 手样本 vs 捕获常量同值）就是这么来的。
3. **不要把「去重跳过 N」当行情健康指标**——它衡量的是簿变更 vs 上报字段变化，见 `doc/md-tick-delivery.md` §6。
4. **不要在断连窗口里「重发」报单**——先查后补（对账），报单不幂等。
