# 行情 tick 的投递契约：同一帧会不会被推两次？（2026-10-29 查证）

> 状态：**结论已查实，代码未改**。归属：本仓 `CtpFrontMdSession.OnTick`（转发 + 逐字节去重）。
> 相关问题：客户端那层「同值去重」该不该有 —— `../../ctp-net-core/doc/md-tick-dedup.md`；tick 在交易所侧是怎么产生的 —— `../../aether-exchange/doc/tick-emission.md`。

## 1. 结论（先看这段）

| 问题 | 答案 |
|---|---|
| 两个 bot 直连交易所，会不会因此让同一帧 tick 被投递两次？ | **不会。** bot 的连线和 tick 的投递路径是两条独立的路：bot 只负责制造成交/簿变更，tick 由交易所产生、前置转发，与 bot 怎么连前置无关（§2） |
| 逐字节相同的两帧会被连续推两次吗？ | **不会。** 前置对每合约的**上一帧**做逐字节比较，相同就吞掉（§4）。实测窗口内吞掉 35 帧 |
| 那客户端日志里「同值 tick 去重 N 条」是什么？ | 是**另一套更弱的判据**：忽略时间戳、只比 8 个量价字段。它挡掉的是「内容相同、时间不同」的**两个不同事件**（§5、§6） |
| 「内容相同、只有时间不同」的 tick 合法吗？ | **合法。** 交易所对每次簿变更都发 tick，第 2 档以下的变化不影响上报帧的内容，但事件时间在前进（§3） |

一句话：**重复投递这件事已经被前置按帧级挡掉了；客户端计数器涨，说明它比错了对象。**

## 2. 路径：谁产生、谁转发

```
下单 ──► SimTradingCore ──► SimMarketDataEngine.RecordTrade / OnBookChanged
                                    │  (每次成交、每次簿变更都发)
                                    ▼
                            TickGenerated 事件  ──►  前置 CtpFrontMdSession.OnTick(tick)
                                                          │  组帧 BuildMdTick（E4F103 流式 op）
                                                          │  逐字节去重（本仓）
                                                          ▼
                                                    RoutePush(frame) ──► 该会话的 CTP 客户端
```

关键点：**bot 不在行情链路上**。bot 连直连会话（`Aether.DirectBot.Console`）还是连前置（`Aether.CtpConsole`），只改变「谁在簿上挂单」；`SimMarketDataEngine` 是唯一的生产者（`RaiseTick` → `TickGenerated`），前置是唯一的转发者（`CtpFrontMdSession.OnTick` → `RoutePush`）。所以「两个 bot 直连 ⇒ 两路 tick」这个推论不成立——不是两个生产者，是一个。

反过来说，**前置几路转发，取决于客户端连了几路**：桌面端、bot 的交易腿、探针脚本各连一条会话就是各收一份。这是「每个客户端一份」的正常语义，不是重复投递。

## 3. 为什么会存在「内容相同、只有时间不同」的 tick

上报帧携带的字段（`CtpFrontTemplates.BuildMdTick`，`CtpFrontTemplates.cs:1039`）：

| 槽 | 字段 | 来源 |
|---|---|---|
| tradingDay | 交易日 | 交易所 |
| updateTime | **HH:MM:SS（8 字节，秒级；无毫秒槽）** | 交易所 tick 的 `UpdateTime` |
| last / volume / openInterest | 最新价 / 累计成交量 / 持仓量 | 交易所 |
| bid / bidVolume / ask / askVolume | 买一价量 / 卖一价量 | 簿顶 |

交易所侧 `OnBookChanged` 对**每一次簿变更**都发（`SimMarketDataEngine.cs:106`），包括第 2–5 档的挂撤单——做市商阶梯撤改每轮都会改这些档，但买一卖一和累计成交量可能一点没变。于是连续两帧的**上报内容完全一致，只有 `UpdateTime` 的秒在走**。

这不是缺陷，是「快照流」的固有语义：交易所没有推送「事件」，推送的是「变更后的快照」；快照的可见部分没变，就必然出现内容重复的快照。真实 CTP 也是如此（`OnRtnDepthMarketData` 是快照流，无序号）。

## 4. 前置去重的确切边界

`CtpFrontMdSession.cs:296-306`：

- **比较对象**：整帧字节（`byte[]` 逐字节比较），因此**时间戳参与比较**；
- **只比前一帧**：每合约一个 `_lastTickFrame`，A→B→A 时 A 会正常通过；不保留历史；
- **按合约独立**：`Dictionary<string, byte[]>`，不同合约互不影响；
- **只影响推送，不影响统计**：被吞的帧只是不发给订阅者，交易所和前置的成交量、持仓统计照旧；
- **会话级**：字典挂在 `CtpFrontMdSession` 实例上，**会话重建（重连）后是空的** ⇒ 重连后的第一帧必然通过，这是唯一能放过「同帧」的窗口（§6）；
- **时间粒度 = 秒**：帧里没有毫秒槽，所以同一秒内、内容相同的两帧会被判为同帧。对「上报内容」而言这是无损的（本来就没有毫秒信息）。

日志语义：`→ 推送 tick: … （去重跳过 N）` 里的 N 是**自上次打印以来**吞掉的帧数，打印后立刻清零（`CtpFrontMdSession.cs:305`），所以这是「突发」读数，不是累计值。

## 5. 实测

### 5.1 前置侧（窗口 15:19:10–16:44:43，`ctpsim-front.log` 的 `Front-MD` 行）

| 观测 | 值 |
|---|---|
| 实际推送 | 169 帧 |
| 被「逐字节相同」吞掉 | **35 帧**（`去重跳过` 采样：17×1 + 6×2 + 2×3） |
| 推送内容去重后 | 75 种 `(last,bid,ask)` 组合 ⇒ 44.4% 唯一（说明 `last` 在动，不是死盘） |

### 5.2 客户端侧原始回调（`AETHER_CTP_TICK_TRACE=1` 下 `[ctp-md] Tick` 行，打印点在去重**之前**）

| 采样 | 原始回调 | 重复（时间 + 6 个量价槽全同） | 内容相同但时间不同 |
|---|---|---|---|
| 43 秒（13:55:30–13:56:13） | 1014 帧 | **0** | 1（订阅快照帧） |
| 5 分钟（13:57:38–14:02:40） | 382 帧 | **0** | **11**（最长连串 3 帧） |

判据说明：逐笔日志打印 `last / bid×bidVol / ask×askVol / vol / HH:MM:SS`，即帧内 8 个会变的槽里的 7 个（缺持仓量）。**真·重复帧是逐字节相同的，必然命中这 7 项**，所以这一列是「有没有重复投递」的可靠下界；第三列则是「除时间外全同」的连对，正是客户端丢的那批。

第二列是这个问题（「同一帧会不会推两次」）的正面回答：**采样里一次都没有**。第三列是客户端计数器涨的原因：11 条全部是「秒在走、8 个量价字段全同」，客户端自己的累计计数也正好是 11（见 `../../ctp-net-core/doc/md-tick-dedup.md` §2）。

## 6. 唯一会真的放过同帧的三处（已知且可解释）

| 场景 | 为什么 | 要不要紧 |
|---|---|---|
| **订阅快照帧** | `PrepareSubscribe` 先经 `quotes` 应答取快照拼成 tick 帧（`volume=0`），随后流式第一帧可能同值 | 不要紧：`volume=0` 的快照与真实成交量是两种信息，客户端第一帧拿到的本来就是这么来的 |
| **会话重建后首帧** | 去重字典是新实例，空表 | 不要紧：一条帧，且时间已前进 |
| **A→B→A** | 只比前一帧 | 不要紧：中间确实换了快照，A 是新的快照 |

除此之外，前置不会把同一帧连续发两次——这是本层的**投递保证**，可以写进契约。

## 7. 结论与建议

1. **前置这层去重保留。** 它挡的是「簿变更引发的重复快照」，逐字节比较、时间参与比较，对上报 schema 无损，是带宽与 native 侧处理的正当优化。真要省电，应该往上游挪一格（在 `SimMarketDataEngine` 只在不重复时发，见 `../../aether-exchange/doc/tick-emission.md`），但前置这层留着当兜底没错。
2. **别用「去重跳过 N」当健康指标。** 它衡量的是「簿变更比上报字段变化多多少次」，与「行情是否活跃」无关；`last` 有没有在动，看 `推送 tick` 行本身。
3. **毫秒级时间戳这件事要在帧模板里解决。** 现在 `updateTime` 只有 8 字节（秒），交易所侧的 `UpdateMillisec` 到不了客户端。任何「同一秒内的两笔 tick 必须区分」的需求（高频回放、逐笔对齐），都要先扩模板，不能靠客户端猜。
4. 客户端那层「同值 tick 去重」多余且会丢真实事件，**已于 2026-10-29 移除**（端点实测前置推 11 帧、客户端交付 12 次回调 = 11 帧 + 1 订阅快照，零丢失）——见 `../../ctp-net-core/doc/md-tick-dedup.md`。
